# MARTA — тестовое задание (README)

**Подход и почему**
- React + чистый Three.js (без R3F) поверх `<img object-fit:cover>` — минимум зависимостей, полный контроль над камерой.
- Камера строится не через Euler→Euler (ловушка порядка осей/handedness), а так: 1) кватернион по формуле UE `FRotator::Quaternion()`, 2) поворот ортов forward/right/up этим кватернионом, 3) ремап осей UE(X,Y,Z)→three(X,Z,Y) — свап Y/Z, одна транспозиция решает смену handedness LH→RH, 4) `camera.quaternion` собирается напрямую из полученного базиса (без lookAt и Euler-конвертаций).
- Вертикальный FOV = `2·atan(sensorH/2/focal)`, горизонтальный — из аспекта картинки (по заданию, ширина матрицы недействительна для скриншотов вьюпорта).
- Респонсив: аналог `object-fit:cover` для 3D-камеры (`applyCoverFit` в `ueMath.js`) — если вьюпорт уже фото, FOV остаётся «родным»; если шире — пересчитывается по формуле cover-fit. Совпадение с кропом картинки сохраняется на любом экране и повороте.

**40 кадров вместо 2, обновление рендера**
- Конфиг камер (`config.js`) — плоский объект; добавление третьей/сороковой камеры не требует правок математики.
- Рендер обновится сам, когда пересоберут сцену в Unreal и обновят `Pogod_XX.jpg` + `Transform_cameras.txt` — пайплайн не завязан на конкретные числа.
- Видеопереход между кадрами (без реализации): анимировать `camera.position`/`quaternion`/`fov` между двумя расчётными камерами на `requestAnimationFrame` — slerp по quaternion, lerp по позиции и fov, ~400–600мс, ease-in-out. Так как подложка — растровый скриншот (не 3D-рендер), стык двух фото можно скрыть под движением камеры (лёгкий блюр/кроссфейд текстуры в середине перехода).

**Как искали позицию модели и что получили**
- Трансформ внутри FBX — мусор (по заданию), позицию искали визуально/численно по обеим фотографиям сразу.
- Спроецировал контур этажа (верх+низ кольца) через обе камеры и решал `(x,y,z)` численно (`scipy`: Nelder-Mead + differential evolution) под совпадение проекции с видимым 7-м этажом корпуса А (4 точки на кадр: xmin/xmax/ytop/ybot).
- По пути нашёл реальный баг: рукописная матрица поворота Pitch/Yaw/Roll→(forward/right/up) была **не ортогональна** при Yaw≠0 (мои тесты на чистом Yaw или Pitch проходили случайно — там ошибка вырождается в ноль). Из-за этого подгонка по кадру 1 не билась с кадром 2. Исправил, посчитав поворот через кватернион UE напрямую — невязка (px²) упала с ~766000 до ~600, проекции легли на нужный этаж на обеих фотографиях.
- Итог: `MODEL_TRANSFORM` в `config.js`. Поворот по Y не понадобился — локальная ориентация меша уже совпадает с миром (форма проекции точно повторяет волну фасада на обоих кадрах).
- Оговорка: позиция найдена по грубым визуальным оценкам пиксельных границ этажа (не по точным контрольным точкам), остаточная ошибка — единицы пикселей на каждой фотографии.
